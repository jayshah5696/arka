## Progress update

There are 11 open issues. The PDF provenance issue is a confirmed bug in the current code and looks like the best small target. I’m checking the filter proposals next to see which offers the strongest follow-up without adding much complexity.

## Recommendation

I would target [#176, exact PDF page provenance](https://github.com/jayshah5696/arka/issues/176) next. I checked all 11 open issues, the current implementation, and recent commits. This is a confirmed correctness bug with a small scope and clear acceptance criteria.

`PDFSourceStage` currently marks every chunk as spanning the entire PDF. It also trims chunk text without adjusting its start offset. That means users cannot reliably trace a chunk to its source. The existing PDF tests cover only one page, so they do not catch the page-range bug.

Keep the change focused on page intervals, exact character offsets, and matching provenance in the payload and source. Write failing tests first for later-page chunks, boundary crossings, empty pages, and trimmed whitespace.

One detail needs correction in the issue before implementation. Record IDs are hashes of the full payload, including provenance. Correcting provenance will change affected record IDs. Preserving those IDs requires a separate compatibility decision.

My suggested order after that is:

1. [#168, repetition-loop filter](https://github.com/jayshah5696/arka/issues/168). This catches unusable responses before expensive judging. It fits the existing filter model and needs no new dependency. First resolve an inconsistency in the brief. The proposed 200-character minimum would let its required `"a" * 100` test pass. Character-run detection should run before that minimum-length gate. Define how overlapping n-grams contribute to the fraction, then check false positives on code and lists.
2. [#177, taxonomy coverage during selection](https://github.com/jayshah5696/arka/issues/177). This is the strongest next feature. The generator already records taxonomy paths, but selection uses only weighted scores. Protecting configured minimum representation would make taxonomy generation useful through the final output. Start with explicit minimum counts and a documented policy for infeasible constraints. Defer share-based constraints if they complicate the first version.
3. [#169, identity-claim filter](https://github.com/jayshah5696/arka/issues/169), then [#171, generation-artifact filter](https://github.com/jayshah5696/arka/issues/171). Both are inexpensive additions, but need careful false-positive checks. Identity claims are the narrower starting point. Artifact stripping also changes text and needs tests for quoted examples and code.

I would hold the remaining work for these reasons:

- [#170, PDF boilerplate stripping](https://github.com/jayshah5696/arka/issues/170). Do provenance first, then define whether offsets refer to text before or after stripping.
- [#167, benchmark decontamination](https://github.com/jayshah5696/arka/issues/167). Move this up if you are about to evaluate a trained model. It needs actual evaluation files and measured false-positive rates.
- [#166, PII redaction](https://github.com/jayshah5696/arka/issues/166). Move this up if your inputs contain personal data. Its proposed stage cannot guarantee that raw PII never reaches any artifact because the runner saves earlier stages. Resolve that scope and the Presidio dependency before implementation.
- [#172, reasoning-language consistency](https://github.com/jayshah5696/arka/issues/172). This needs reasoning support across generation and export first. Avoid the proposed silent pass-through when its language model is missing.
- [#165, distilled quality scoring](https://github.com/jayshah5696/arka/issues/165), and [#173, audit-and-regenerate](https://github.com/jayshah5696/arka/issues/173). These need measured judge costs or failure rates to justify the added training and checkpoint complexity.

My pick is #176 for the next fix, followed by #168. Choose #177 if you want the next substantial feature.
