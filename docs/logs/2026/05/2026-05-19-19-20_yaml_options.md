Here are the two main ways we can handle the configuration design and schema validation:

### Option 1: Keep the Current Fixed Layout
Keep the current YAML blocks (`data_source`, `generator`, `dedup`, `filters`) as is, but generate a standard `schema.json` to validate them and provide auto-complete.
- **Pros:** No breaking changes. Existing YAML config examples don't need rewriting.
- **Cons:** Ordering is hardcoded. Cannot run custom combinations (e.g. run a transform, filter it, run another transform, deduplicate it) in a single run.

### Option 2: Transition to a Unified `pipeline` List
Combine all steps (ingestion, generation, deduplication, filtering, transformations) into a single ordered list under a `pipeline` key:
```yaml
pipeline:
  - type: seed_source
    path: ./seeds.jsonl
  - type: prompt_generator
    target_count: 10
  - type: exact_dedup
  - type: length_filter
    min_response_chars: 50
```
- **Pros:** High flexibility. Users can reorder steps, repeat them, or run complex loops (like generation -> filter -> rewrite -> filter) in a single run. Very clean schema definition via Pydantic unions.
- **Cons:** Breaking change. Requires updating the 8 example YAML files in `examples/` and updating the runner logic to iterate directly over a single stage list from the config.
